# Технические решения

Решения на 24 сентября 2026 года; пересматриваются при конкретной проблеме,
а не ради добавления технологий в резюме.

| Решение                               | Причина                                                              | Компромисс                                              |
| ------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------- |
| React + Vite                          | Знакомый пользователю стек; основной продукт — интерактивный кабинет | SSR/SEO лендинга решаем позже отдельно                  |
| TypeScript во всех приложениях        | Общие контракты и безопасный рефакторинг                             | Внешние данные всё равно требуют runtime-валидации      |
| Node.js 24 LTS                        | Единый runtime разработки и CI                                       | Текущий default Node 20.15.1 нужно заменить для проекта |
| Fastify API                           | Явная HTTP-граница и отдельный жизненный цикл от браузеров           | Нужны собственные auth и deployment wiring              |
| PostgreSQL + Graphile Worker          | Данные и очередь в одной транзакции; меньше инфраструктуры           | At-least-once требует идемпотентных задач               |
| Drizzle + SQL migrations              | Типизированные запросы и видимая схема                               | Миграции и ограничения проектируем явно                 |
| Отдельный worker и изолируемый runner | Браузерная нагрузка и внешние сайты отделены от HTTP API             | Сложнее локальный запуск и деплой                       |
| Polling активного Run                 | Достаточно для небольшого числа запусков                             | Прогресс приходит с задержкой до нескольких секунд      |
| PNG diff с подтверждённым baseline    | Понятный результат с проверяемым доказательством                     | Требует стабильной среды, масок и настройки порога      |
| Chromium и два viewport               | Реалистичный объём на месяц                                          | Это не полная кроссбраузерная или мобильная проверка    |
| npm workspaces                        | Достаточно для трёх приложений и общих пакетов                       | Команды сборки первоначально задаём явно                |

## Дизайн отчёта — 25 сентября 2026

Пользователь утвердил B — Release Console: тёмная палитра с голубым акцентом,
очередь замечаний слева, сравнение справа. Используем это направление для
рабочего отчёта. Конкретный прототип и границы реализации — в design-review.md.

## Восстановление Run — 26 сентября 2026

Для локального MVP используем deadline попытки в PostgreSQL (две минуты),
сверку в API раз в 15 секунд и при старте worker. Просроченный Run получает
failed/inconclusive; late completion проверяет deadline и terminal state в БД.
Повтор пользователем создаёт новый Run, сохраняя свидетельства сбоя в истории.

Причина: стандартное [восстановление Graphile после аварии](https://worker.graphile.org/docs/error-handling)
оставляет job заблокированным на несколько часов. Принудительная разблокировка
требует доказательства остановки worker. Сейчас мы не строим отдельный heartbeat
cluster: ограниченный сценарий с одной страницей может завершиться ошибкой
и быть явно запущен заново. Private tables Graphile не изменяем.

Queued job без worker сохраняется для последующего старта. Ошибки обычного
исполнения по-прежнему повторяются Graphile; не путаем backoff с hard crash.
Перед расширением до нескольких страниц пересматриваем budget и partial results.

## Вопросы, которые решаем позже

- Hosting и бюджет: после измерения времени и памяти одного Run.
- Провайдер S3: после выбора hosting; интерфейс хранения не зависит от него.
- Точные версии библиотек: при scaffolding с lockfile и проверкой совместимости.
- Объём хранения и retention: после измерения сценариев.

Не добавляем Redis, Kubernetes, отдельные микросервисы для каждого вида проверок
и AI-функции в первоначальную архитектуру: в текущем объёме у них нет задачи.

## Настройки сравнения (26 сентября)

Допустимая доля изменённых пикселей хранится целыми basis points (0–500),
UI показывает проценты с шагом 0.01. Это отдельный параметр от фиксированного
pixelmatch threshold 0.1, определяющего отличие каждого пикселя.
Версия защищает сохранение между вкладками. Project update и enqueue используют
общий advisory lock: Run получает целиком старую или новую конфигурацию.
Изменение tolerance не требует новой baseline: исходное изображение и capture
profile прежние, меняется только критерий сравнения будущих запусков.

## Два размера, один capture на Run (27 сентября)

Расширяем Run перечислением desktop/mobile, а не произвольными размерами.
Worker получает размеры из snapshot и валидирует только разрешённые пары.
Существующий profile hash включает width/height; baseline candidates дополнительно
фильтруются по размерам исходного capture, чтобы первый mobile запуск корректно
показывал отсутствие baseline, а не несовместимость desktop окружения.
Mobile остаётся responsive viewport без изменения UA/touch. Это сохраняет явные
границы обещаний продукта и независимость capture от размеров окна приложения.
Batch-запуски нескольких страниц/viewport потребуют PageResult и partial results;
их не подменяем увеличением текущего deadline.

## Ограниченный HEAD link check (27 сентября)

Link evidence хранится отдельно от browser findings: HTTP 404 ресурса при
загрузке страницы и HTTP 404 гиперссылки — разные наблюдения. Сначала screenshot,
затем HEAD requests без cookie и redirect following. DOM учитывает resolved href
(включая base URL), а runner повторно проверяет origin. Нет внешнего обхода.
Не используем GET fallback для серверов без HEAD: сохраняем unverified и
inconclusive вместо ложного pass. Лимиты оставляют проверку внутри текущего
60-секундного runner budget. Это контракт для контролируемого демо; публичные
URL требуют отдельной сетевой изоляции и политики безопасных запросов.
