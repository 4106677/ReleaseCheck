# Локальная разработка

## Окружение

Node.js 24 (`.nvmrc`), npm, Docker Compose. Всё запускается из корня репозитория.
`.env`, `.artifacts`, `.local`, зависимости и скриншоты тестов исключены из git.
Локальные credentials в `.env.example` предназначены только для контейнера проекта.

Если `nvm` не установлен, используйте любой менеджер Node.js с версией 24.
Не запускайте Vite под старым системным Node.js 20.15.1.

| Процесс    | Адрес                 | Назначение                                   |
| ---------- | --------------------- | -------------------------------------------- |
| Web        | http://127.0.0.1:5173 | React-интерфейс, `/api` проксируется в API   |
| API        | http://127.0.0.1:3001 | Создание запусков, история, результаты и PNG |
| Fixture    | http://127.0.0.1:4174 | Контролируемый storefront                    |
| PostgreSQL | 127.0.0.1:55432       | Данные приложения и очередь Graphile Worker  |

## Команды

Первичная установка описана в [README](../README.md). `npm run dev` сначала
собирает workspaces, затем запускает четыре процесса и завершает остальные,
если один из них остановился. Ctrl+C завершает локальный стек; БД продолжает работать.
`docker compose stop` останавливает БД, сохраняя volume.

React обновляется через Vite HMR. После изменения backend или общих пакетов
перезапустите `npm run dev`: они сейчас исполняются из скомпилированного `dist`.
Watch-сборка общих пакетов пока не добавлена.

- `npm run build` — сборка пакетов и приложений в порядке зависимостей.
- `npm run typecheck` — сборка и проверка типов integration/unit-тестов.
- `npm run lint` — ESLint.
- `npm test` — unit-тесты на собранных пакетах.
- `npm run check` — сборка, типы, lint и unit-тесты.
- `npm run test:integration` — реальная БД и браузер; нужны сборка и `TEST_DATABASE_URL`.
- `npm run test:smoke` — цикл baseline → сравнение → принятие через UI; нужен работающий локальный стек.
  Скрипт сохраняет новые запуски и явно подтверждает эталоны демо-проекта.
- `npm run test:recovery-ui` — error/retry UI с подменёнными ответами API, включая мобильную ширину.
- `npm run test:design` — оба дизайн-прототипа, ползунок, diff, выбор issue, modal и mobile.
- `npm run design:assets` — реальные before/after/diff для прототипов; нужны fixture и сборка packages.
- `npm run format` / `npm run format:check` — форматирование.
- `npm run db:migrate` — миграции Graphile и приложения, с checksum уже применённых SQL.

Integration-тесты используют отдельную disposable-БД с суффиксом `_test`, удаляют
из неё историю запусков и временно переименовывают схему очереди для проверки отката.
Не направляйте `TEST_DATABASE_URL` на БД с полезными данными.

## Как устроен первый сквозной путь

1. UI отправляет `POST /api/projects/<demo-id>/runs` с вариантом и Idempotency-Key.
2. Под блокировкой проекта API проверяет повторный ключ и наличие активного запуска.
3. Run и job создаются в одной PostgreSQL-транзакции. Повторный ключ с другим
   вариантом даёт 409; другой запуск при активной проверке — тоже 409.
4. Worker сохраняет номер попытки и передаёт конфигурацию отдельному runner-процессу.
   В его окружение не передаётся DATABASE_URL. Это разделение процессов, не
   production-изоляция для недоверенных сайтов.
5. Chromium получает только заранее заданный loopback fixture. Он собирает
   ошибки страницы и сети, ждёт сигнал готовности fixture и делает PNG 1440×900.
6. Worker атомарно записывает PNG, затем фиксирует результат и ссылку на артефакт
   в транзакции. Устаревшая попытка не может перезаписать результат новой.
7. UI получает статус через polling; опрос завершённого запуска останавливается.

Вариант `baseline` означает исходную версию fixture. Эталон создаётся только
явным подтверждением в UI или `POST /api/projects/:id/baselines` с
`{ runId, expectedVersion }`. `GET /api/runs/:id/baseline` возвращает текущую
версию для профиля захвата; первая версия ожидает `expectedVersion: 0`.
Совпавший повтор принятия возвращает ту же версию, конфликтующий — 409.
Автор локального решения — `local-dev-user`, OAuth пока отсутствует.

Эталон хранится по профилю (browser/OS/viewport/settings), версии добавляются,
а не перезаписываются. Создание Run сохраняет актуальные эталоны и пороги сравнения
под той же блокировкой проекта, что и принятие. Worker использует этот снимок,
поэтому смена эталона не влияет на queued или завершённые Run.

Без эталона или при несовместимом профиле — `inconclusive`; совпадение без browser
findings — `pass`; визуальные изменения выше порога или browser findings —
`attention`. Недоступная страница — `failed / inconclusive`.
Старые захваты без профиля остаются доступны, но не могут стать эталоном:
нужно сделать новый запуск. Capture и diff фиксируются вместе с результатом
в одной транзакции с проверкой актуальности попытки.

## Наблюдения и группы проблем

Capture сохраняет исходный массив findings. Новые наблюдения содержат method,
resourceType и status для запросов, source URL/позицию console-сообщения,
ограниченный 4000 символами стек JS-ошибки. Поля необязательны: старые захваты
читаются без миграции и без подставленного контекста.

Чистая функция `groupFindings` в contracts используется только для представления:

- Точные повторы объединяются с учётом всех сохранённых полей.
- Специфическое HTTP failure console-сообщение Chromium связывается с единственной
  HTTP-группой с тем же полным URL и status. Method/context разных HTTP-групп
  создают неоднозначность — console остаётся отдельно.
- Query string сохраняется; обрезанный URL, отсутствующий status/source или
  произвольный console-текст не используются для предположений.
- Каждое входное наблюдение встречается в результате ровно один раз. Порядок
  внутри группы соответствует исходному capture; данные не изменяются.

Browser issues показывает группы, observations — исходное количество.
Original evidence раскрывает сообщения и контекст, включая повторы. Группировка
не меняет verdict и не доказывает, что совпавшие URL относятся к одному запросу:
повторные запросы к ресурсу остаются видны отдельными наблюдениями.
У старых capture без контекста возможны дополнительные раздельные группы.

## Восстановление прерванной проверки

Миграция 003 добавляет `attempt_deadline`. При claim PostgreSQL задаёт попытке
две минуты: это запас к 60-секундному лимиту runner для текущей одной страницы.
Обычные infrastructure-ошибки по-прежнему получают до трёх попыток Graphile;
попытка с истёкшим deadline уже не может быть начата или опубликовать результат.

API запускает сверку сразу при старте и затем через 15 секунд после окончания
предыдущей сверки. Worker также выполняет её перед началом обработки очереди.
Сверка читает публичный view `graphile_worker.jobs` и завершает активные Run:

- `RUN_DEADLINE_EXCEEDED`: истёк deadline попытки либо queue lock старше двух минут
  (в том числе падение между получением job и claim).
- `CAPTURE_INFRASTRUCTURE_FAILED`: задача исчерпала попытки и больше не исполняется.
- `QUEUE_JOB_MISSING`: задача отсутствует в очереди.

Живую последнюю попытку не завершаем только из-за `attempts === max_attempts`.
Ожидающая задача без worker остаётся queued и может продолжиться после его старта.
Исторические completed/failed Run не изменяются. Несколько сверок не мешают друг
другу: `FOR UPDATE SKIP LOCKED`, до 100 активных Run за проход. В текущем демо
активный Run один. Таймер не запускает параллельные проходы, повторяет запрос
после ошибки БД и останавливается до закрытия пула в `preClose`.

Для обнаруженного hard crash выбрана политика failed + явный новый Run через
**Retry check**, с тем же вариантом страницы и текущим baseline. Она не требует
принудительно снимать queue lock с потенциально живого worker. Старый job позднее
либо остаётся в failed queue до обслуживания, либо доставляется повторно и
ничего не публикует благодаря terminal state. Удаление старых jobs/файлов —
отдельный этап retention.

При работающих API и БД running-проверка обычно получает ошибку не позднее
двух минут плюс интервал сверки. При отключённой БД/всех процессах восстановление
происходит после возвращения сервиса. Это deadline выполнения, а не доказательство
смерти процесса; автоматическое продолжение hard-crashed попыток пока не реализовано.

## Проверенные сценарии

Unit: допустимые варианты и конфигурация fixture, ключи повторов, terminal states,
безопасные storage keys, атомарная запись PNG, сравнение изображений и lifecycle
recovery-таймера (ошибка БД, отсутствие перекрывающихся проходов, остановка).
Также lossless-группировка: порядок событий, неоднозначные методы, разные статусы,
query strings, legacy/обрезанный контекст и различающиеся стеки.

Integration: конкурентные повторы, конфликт вариантов, лимит активного запуска,
откат при недоступной очереди, сохранение queued-задачи после пересоздания API,
реальный PNG, JS/HTTP findings, недоступный fixture и защита от устаревшей попытки.
Также: подтверждение и повтор baseline, конкурентные решения, queued snapshot,
несовместимые профили, legacy capture и сохранение ошибок после принятия внешнего вида.
Recovery suite запускает отдельный Graphile worker и завершает его SIGKILL на
последней попытке, проверяет API-таймер, новый реальный захват, позднюю публикацию,
параллельные сверки, backoff, exhausted/missing jobs и восстановление при старте worker.
Для ускорения тест меняет только deadline доменной строки, не private tables очереди.

Browser smoke: принятие исходного эталона, совпадение, visual diff, подтверждение
изменённой версии, неизменность JS/network findings. Также Escape в диалоге,
управление запуском на ширине 390 px, отсутствие ошибок самого React-приложения
и горизонтального переполнения. Проверены счётчики групп/наблюдений и раскрытие
Original evidence клавишей Enter с двумя исходными сообщениями HTTP/console. Скриншоты — `.local/smoke/`.
Recovery UI smoke подменяет HTTP-ответы: проверяет понятную ошибку, отсутствие
ложных screenshot/baseline controls и повтор с исходным variant и стабильным
idempotency key после 503. Его снимки — `.local/recovery/`.

CI использует Ubuntu 24.04. Для загруженного Chromium устанавливается профиль
AppArmor, разрешающий user namespaces только двум browser executable в cache
текущего job. Chromium sandbox и общая политика AppArmor остаются включены.
Скрипт `scripts/ci-browser-sandbox.sh` отказывается работать вне GitHub-hosted Linux.

## Ограничения текущей реализации

- Один demo-проект, одна страница, один desktop viewport; нет пользователя и OAuth.
- История ограничена последними 20 запусками, без cursor pagination.
- Нет link checker, mobile capture и удаления истории. Browser observations
  группируются по строгим правилам; для transport/JavaScript пока нет корреляции
  причин между разными видами событий.
- Recovery работает по deadline, без heartbeat и автоматического продолжения
  hard-crashed попыток; пользователь начинает новый Run. Для нескольких страниц
  и viewport бюджет времени нужно пересмотреть вместе с моделью PageResult.
- После сбоя между загрузкой файла и фиксацией БД могут остаться неиспользуемые
  PNG; автоматическая очистка появится с retention. Ссылки на отсутствующие файлы
  не публикуются до завершения записи файла.
- Нет контейнерной изоляции и egress-политики runner, поэтому внешние URL
  недоступны через API и production-запуск явно запрещён.
- Один профиль соответствует единственной странице и viewport демо. При добавлении
  страниц/viewport ключ baseline нужно расширить до модели целевой архитектуры.

Эти ограничения относятся к текущему шагу, а не отменяют утверждённую
[целевую архитектуру](architecture.md).
